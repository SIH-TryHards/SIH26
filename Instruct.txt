KISAN SAATHI WEB DEVELOPMENT INSTRUCTION FILE

Purpose

This file is the operating instruction for the agent team that will complete the web development of D:\SIH26-TryHards. The target product is Kisan Saathi: a minimal, low-bandwidth, multilingual farmer advisory web app with a separate officer dashboard for distress-risk review and follow-up action.

The final website must keep the existing Kisan Saathi look: clean, calm, green, text-first, mobile-friendly, low visual noise, and easy for farmers to use. The folder D:\SIH26-TryHards\krishi sethi is a source of implementation ideas and feature logic only. Do not copy its heavy theme, visual style, Tailwind-heavy layout, hero image style, large decorative sections, or dense UI patterns into the main project.

Primary Rule

Build on top of the current Kisan Saathi project. Do not restart the app, do not replace the existing architecture, and do not overwrite completed working sections unless a change is required and verified.

Current Product Direction

Kisan Saathi has two role-specific experiences:

1. Farmer application
   The farmer chooses language, completes onboarding, signs in with phone OTP, manages farm and crop information, reads/listens to crop advisories, compares mandis by practical net return, uses a loan planner, gets support information, and contacts the assigned officer.

2. Officer dashboard
   The officer signs in, sees only assigned jurisdiction data, reviews explainable HIGH/CRITICAL distress cases, records intervention actions, and follows up without exposing private risk scoring to farmers.

3. Decision services
   Weather, mandi prices, advisory rules, loan factors, and risk scoring must remain behind clear service/repository boundaries so demo mode works offline and live adapters can be swapped in later.

Design Guardrails

Keep:

- Existing Kisan Saathi minimalist visual language.
- Static HTML, CSS, and vanilla JavaScript style unless the project has already adopted something else.
- Low-bandwidth farmer-first layout.
- Large readable text, clear labels, short actions, and predictable navigation.
- Existing language-first onboarding and account setup flow.
- Existing repository/service boundary.
- Farmer privacy: farmers must never see distress score, risk band, or officer-side risk labels.

Avoid:

- Copying Krishi Sethi UI, theme, hero image treatment, decorative cards, or large marketing sections.
- Adding framework churn unless required by the current codebase.
- Adding Aadhaar, PAN, bank, biometric, real loan disbursement, or official financial transaction features.
- Hardcoding API keys, tokens, phone numbers, passwords, or cloud credentials.
- Writing live API logic directly inside UI components.
- Breaking existing completed flows while adding new screens.

Required Tech Stack and Tools

Use the current stack unless there is a confirmed blocker:

- Frontend: HTML5, CSS3, vanilla JavaScript ES modules.
- Styling: existing assets/css/app.css design tokens and components.
- State: existing local storage and repository pattern.
- Routing: existing in-app router pattern.
- Icons: existing local icon helper or a lightweight existing icon approach already present in the app.
- Backend: FastAPI.
- Database: SQLite for local demo, PostgreSQL-ready schema discipline for future deployment.
- Migrations: Alembic-style migration discipline when schema changes are introduced.
- Auth: phone OTP for farmers, staff/password for officers in demo, JWT/session-ready boundary for production.
- Weather: Open-Meteo through backend adapter with deterministic simulator fallback.
- Mandi: data.gov.in or Agmarknet-style backend adapter with deterministic/cache fallback.
- Voice: browser SpeechSynthesis first; do not port cloud TTS credentials from Krishi Sethi.
- Testing/verification: browser run, console check, mobile viewport check, backend endpoint check, and manual flow checklist.

Source Folder Usage: Krishi Sethi

Use D:\SIH26-TryHards\krishi sethi only as a reference for feature behavior.

Extract or port:

- Mandi discovery behavior.
- Nearby mandi ranking ideas.
- All-goods or crop-wise rate card logic.
- Distance calculation concepts.
- Weather fallback behavior.
- Crop advisory content patterns.
- Soil/location suggestions.

- Government scheme content structure.
- Officer queue/action ideas.
- Data cache strategy where useful.

Do not port:

- Its theme, layout, hero sections, background imagery, Tailwind styling, or dense visual composition.
- Its auth modal as-is.
- Any hardcoded key, token, credential, password, or secret.
- Direct browser calls that expose private API keys.

Security note:

If any credential-like value is found in Krishi Sethi, treat it as compromised reference material. Do not copy it into Kisan Saathi. Replace with environment variables, backend adapters, or local placeholders.

Agent Team Roles

Kisan Overseer - Workflow Manager

Responsible for making sure the whole bot farm follows this instruction file. Overseer checks that Commander, Forge, Sentinel, and Seal are working in sequence, not duplicating work, and not overwriting stable implementation. Overseer stops the loop after each module so the human can review.

Kisan Command - Product Workflow Commander

Responsible for giving exact module-by-module direction. Command reads pathway.md, current code, and this Instruct.txt before assigning work. Command must describe what to implement from existing resources, what to ignore, which files are likely involved, and what acceptance criteria must be met.

Kisan Forge - Implementation Engineer

Responsible for making the requested small implementation. Forge must follow existing code style, keep edits scoped, avoid broad rewrites, and preserve completed screens. Forge implements one small module at a time and stops after the module is working.

Kisan Sentinel - OS, Runtime, and Integration Verification Engineer

Responsible for checking whether the implementation actually works. Sentinel runs the app, checks browser behavior, checks console/runtime errors, verifies responsive layout, confirms data flow, and reports exact failures back to Forge.

Kisan Seal - Release Finalizer and Change-Protection Engineer

Responsible for final review of a completed module. Seal confirms no stable feature was broken, no private farmer risk is exposed, no hardcoded secrets were added, and the implementation is clean enough for the next module.

Standard Workflow Loop

Every module must follow this loop:

1. Overseer confirms the current target module.
2. Command reads current files and writes a short implementation order.
3. Forge implements only that order.
4. Sentinel runs and verifies the module.
5. Forge fixes issues found by Sentinel.
6. Sentinel rechecks.
7. Seal reviews the final diff and protects completed work.
8. The team stops and asks the human to review before the next module starts.

No agent should skip verification. No agent should continue into the next module without human review.

Goal:
Make account setup feel professional and complete while preserving the current minimal style.

Required farmer path:

- Onboarding/profile draft.
- Account intent screen.
- Phone entry.

Make weather and mandi data cleanly swappable between simulated and live sources.

Required interfaces:

- WeatherProvider: simulated and live Open-Meteo adapter.
- PriceProvider: simulated/cache and live mandi adapter.

Acceptance:

- App works with no network.
- App can call backend live adapter when configured.

- No API key is exposed in frontend code.

Implementation Rules for Every Module

- Work in small increments.
- Read before editing.
- Use existing file structure.
- Prefer small helper functions over large rewrites.
- Do not duplicate data definitions across multiple files unless the project already does so.
- Keep business logic separate from DOM rendering where practical.
- Keep UI text language-ready.
- Use integer paise or plain rupees for money; do not use floating money storage.
- Use UTC timestamps in data and render user-facing time in local context.
- Keep deterministic seed/demo behavior stable.
- Do not introduce a new package manager, framework, bundler, or design system without a concrete need.
